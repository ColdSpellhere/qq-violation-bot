# 机器人模块化功能控制设计

日期：2026-08-21
状态：已确认，待实施

## 1. 目标

将现有机器人拆分为相互独立的“业务功能”和“聊天功能”，并提供可持久化的运行时开关。管理员应能通过 QQ 指令即时止损，无需修改代码、重启服务或回滚版本。

本次只调整模块边界、消息路由、开关和失败消息补偿，不改变现有业务数据结构、聊天人格、接话概率、记忆提炼规则或表情包权重。

## 2. 功能边界

### 2.1 业务功能

业务功能仅对当前已有业务的群开放，其他群永远不进入业务判断。

业务功能包括：

- 违规记录、查询、导出和相关管理操作；
- 扣分、减停判断和提醒；
- 业务定时任务、待发送队列及主动通知。

关闭业务功能后：

- 停止接受和处理新的业务请求；
- 停止发送业务提醒和主动通知；
- 保留全部业务数据库内容，不删除、不回滚数据；
- 当前业务群如果同时位于聊天群白名单中，仍可正常聊天。

### 2.2 聊天功能

聊天总开关统一管理以下能力：

- 群聊回复和随机接话；
- 私聊回复；
- 消息归档；
- 成员身份与特性记忆；
- 共享的 AI 人格、上下文和表情包能力。

聊天总开关关闭后，上述能力全部暂停。群聊和私聊另设子开关与独立白名单。

群聊规则：

- 只处理聊天群白名单中的群；
- 白名单群内明确艾特机器人时必定回复；
- 普通聊天继续按现有随机接话概率决定是否回复；
- 消息是否触发回复不影响归档和成员记忆；
- 关闭群聊子开关后，群聊回复、归档和成员记忆一起暂停，私聊不受影响。

私聊规则：

- 私聊子开关开启且发送者位于 QQ 白名单时才处理；
- 关闭私聊子开关只影响私聊，不影响群聊、归档和成员记忆；
- 群聊和私聊共享人格与表情包，但上下文相互隔离。

## 3. 推荐架构

采用“插件固定加载、统一功能门控、薄消息路由”的结构，不在运行时动态卸载 NoneBot 插件。

### 3.1 功能控制层

新增统一功能控制服务，提供以下状态：

- `business_enabled`
- `chat_enabled`
- `group_chat_enabled`
- `private_chat_enabled`
- `group_chat_allowed_group_ids`
- `private_chat_allowed_user_ids`

当前业务群继续由独立配置指定，不允许通过聊天群白名单改变其业务权限。

所有 matcher 和定时任务在执行关键动作前查询统一状态。这样可以即时关闭功能，又避免动态卸载造成 matcher、缓存或定时任务残留。

### 3.2 群消息路由

路由顺序如下：

1. 判断消息是否来自当前业务群。
2. 若来自业务群且业务功能开启，明确业务命令或已识别的业务意图交给业务处理器。
3. 未识别为业务的普通消息，在聊天功能开启且该群位于聊天白名单时交给聊天处理器。
4. 其他聊天白名单群完全跳过业务识别，只进入聊天流程。
5. 不满足任何开关或白名单条件时静默忽略。

业务模块不再直接导入或调用聊天回复函数。业务意图为未知时由路由层决定是否转交聊天，从而保持两类功能相互独立。

### 3.3 记忆与归档

消息归档和成员记忆属于聊天功能，并与群聊子开关及聊天群白名单绑定。

关闭聊天总开关或群聊子开关时：

- 不再归档新群消息；
- 不再加入新的记忆提炼批次；
- 已进入等待队列但尚未执行的记忆任务在回调时再次检查开关，关闭状态下不写入。

重新开启后只处理新消息，不回放关闭期间的群聊。

## 4. 运行时管理

只有 NoneBot `SUPERUSERS` 可以执行管理指令：

- `/模块状态`
- `/业务 开|关`
- `/聊天 开|关`
- `/群聊 开|关`
- `/群聊群 添加 <群号>`
- `/群聊群 删除 <群号>`
- `/群聊群 列表`
- `/私聊 开|关`
- `/私聊用户 添加 <QQ号>`
- `/私聊用户 删除 <QQ号>`
- `/私聊用户 列表`

非超级管理员执行时拒绝操作，不返回内部白名单详情。

运行状态写入服务器 `data/runtime_features.json`，不提交 Git。写入采用临时文件加原子替换，并保留上一份有效备份。`.env` 仅提供首次启动默认值；存在有效运行时状态时，以运行时状态为准。

总开关关闭时不清除子开关和白名单。重新开启总开关后恢复原有子配置。

写入失败时保持旧状态并向管理员明确报错，不返回虚假的成功提示。

## 5. 未发送业务提醒补偿

业务关闭期间错过的提醒、QQ 离线期间无法发送的提醒，以及 OneBot/API 明确返回失败的提醒，统一进入未发送记录。

恢复条件包括：

- 业务功能由关闭切换为开启；
- QQ/OneBot 连接恢复；
- 后续定时检查发现发送通道恢复。

恢复后不逐条补发原始提醒，只向当前业务群发送一次合并转发概览。概览包括：

- 未发送时间范围；
- 涉及人数；
- 各类提醒数量；
- 每人的简要事项；
- 未发送原因（业务关闭、QQ 离线或发送失败）。

内容较多时拆成多个合并转发节点，但仍只产生一次群内提示。相同业务事项按稳定标识去重。

只有合并概览发送成功后，相关未发送记录才标记为已处理。概览发送失败时继续保留，等待下次恢复重试。原始业务记录始终保留。

## 6. 兼容与上线原则

- 首次升级默认继承当前生产开关和白名单，避免升级后功能突然变化；
- 现有 `TARGET_GROUP_ID` 可在迁移期作为当前业务群配置来源；
- 现有两个私聊白名单 QQ 迁移到多值私聊白名单；
- 当前接话概率、人格、表情包和记忆数据保持不变；
- 开关状态和白名单运行数据不进入 Git；代码、示例配置和文档进入版本控制；
- 出现异常时优先通过 QQ 管理指令关闭单一模块，不需要回滚整个机器人。

## 7. 验证范围

采用聚焦测试，不扩展复杂测试工程。至少覆盖：

- 总开关与子开关的门控关系；
- 业务群、聊天群和私聊 QQ 白名单；
- 业务意图与普通聊天的路由隔离；
- 艾特必回和普通消息概率接话的边界；
- 归档、成员记忆与聊天开关的绑定；
- 运行状态原子持久化及重启恢复；
- 未发送提醒的去重、汇总、发送成功确认和失败保留；
- 业务关闭后不发送提醒，聊天仍可独立工作。

上线验证还应确认机器人进程、NapCat/OneBot 连接、当前业务群业务命令、聊天白名单群艾特回复及两个授权 QQ 的私聊。

## 8. 后续扩展：OA 集中管理

后续计划建设 OA 管理平台，对机器人模块、群白名单、私聊白名单、运行状态和未发送提醒进行集中管理。本次不实现 OA 页面或接口。

本次功能控制服务应保持单一读写入口，避免插件直接读取 JSON 文件。未来 OA 只需调用同一服务或其上层 API，无需重写业务、聊天插件和消息路由。管理操作应预留操作者、时间和变更前后值等审计字段的扩展空间。
